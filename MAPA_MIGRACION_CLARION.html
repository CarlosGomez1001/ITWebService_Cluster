Mapa de migración Clarion → React + PHP

Cómo un módulo legacy de Clarion (ITRentas) pasa por el análisis, el contrato MODULE-SPEC v2, la revisión humana, la implementación y la revisión de conformidad, y qué agente o skill de Claude Code interviene en cada paso.

● Agente ● Skill ● Artefacto / contrato ● Compuerta humana ● Fuente legacy ● Retorno / bucle

Etapas en detalle

0

Preparar la petición (opcional)

prompt-enhancer

Si la petición llega vaga ("migra facturación"), la skill prompt-enhancer del cluster la reescribe con el módulo, las capas, las skills aplicables, el orden front/back y los criterios de aceptación antes de tocar código.

1

Fuente legacy

Clarion ITRentas
Dónde vive
  • migrations/ITRentas/*.txa: 238 archivos, incluido __GLOBAL__.txa
  • migrations/Modulos/<modulo>/txa/: el subconjunto del módulo
Ejemplo: pedidos-cliente
  • BrowsePedidosClientes.txa
  • UpdatePedidosCliente.txa
  • UpdateConPed.txa
Si falta una dependencia (DCT, stored procedure, rutina global), se registra como evidencia faltante. Nunca se inventa.
2

Análisis legacy

clarion-expertclarion-analysisbusiness-rule-extraction

Objetivo: Clarion → comportamiento observable → semántica de negocio → MODULE-SPEC v2. No traduce sintaxis de Clarion a React/PHP. Herramientas: Read, Grep, Glob y Skill; no escribe código.

clarion-analysis
  • Inventario: procedimientos, ventanas, tablas, SPs y dependencias
  • Separa la señal (embeds, eventos, SQL, validaciones, cambios de estado) del ruido generado (geometría, fuentes, plumbing)
  • Clasifica: UI, BUSINESS_RULE, VALIDATION, DATA_ACCESS, SQL, WORKFLOW, SIDE_EFFECT…
business-rule-extraction
  • Reglas atómicas BR-* (SI/CUANDO → ENTONCES)
  • Workflows WF-*, políticas POL-*, máquinas de estado SM-*
  • Contratos de datos DC-*, efectos SE-*, pendientes UNR-* y trazabilidad
Orden sugerido
  • Inventario → ruido → dominio → matriz de conceptos → permisos → inventario/reservas → workflows → estados → contratos → efectos → UNR → trazabilidad
3

Contrato de migración

MODULE-SPEC.v2.jsonschema

Es el único artefacto de entrega entre el análisis y la implementación. Se valida contra migrations/schemas/MODULE-SPEC.v2.schema.json, y la guía está en migrations/MODULE-SPEC.v2-GUIDE.md.

Secciones
  • module · legacy_sources · domain · capabilities · rules · workflows · policies · state_models · data_contracts · side_effects · architecture_mapping · traceability · unresolved · review
Confianza de cada conclusión
  • confirmed: evidencia directa o decisión humana
  • inferred: interpretación sólida, sin prueba directa
  • unresolved: la intención no se puede establecer
Artefactos de apoyo (piloto)
  • framework/CONCEPT-TYPE-MATRIX.v1
  • framework/AUTHORIZATION-MATRIX.v1
  • framework/INVENTORY-RESERVATION-WORKFLOW.v1
  • framework/INVOICE-WORKFLOW.v1
4

Revisión humana

compuertareview.status

La persona responsable aprueba o rechaza los UNR-*, los bugs del legacy, los cambios de semántica y lo que intencionalmente no se migra. Las decisiones quedan en review.decisions, y review.status pasa de review_required a approved.

Sin approved, el orquestador solo entrega un reporte de preparación y no implementa lógica crítica.
5

Implementación

migration-orchestrator

Consume solo el spec aprobado y la arquitectura del proyecto. No relee Clarion para reinterpretar el negocio: si falta información, reporta un SPEC GAP. Herramientas: Read, Grep, Glob, Write, Edit, Bash, Skill y Agent.

Secuencia por capacidad
  • Leer el spec → resolver IDs → mapear a la arquitectura → plan
  • Límites de transacción
  • Backend/dominio → persistencia → frontend
  • Tests → trazabilidad → validación
Patrón para escrituras complejas
  • Build Plan → Validate Plan → Apply in Transaction (p. ej. InvoicePlan, DispatchPlan, ReservationPlan)
Autoridad del backend
  • Permisos, validación, inventario, cálculos financieros, transiciones de estado, transacciones y efectos. El front solo los refleja para la UX.

El orquestador delega en los agentes y skills del proyecto que estén disponibles. Estos son los de cada repo hijo:

6

Revisión de conformidad

migration-reviewersolo lectura

Compara MODULE-SPEC ↔ implementación ↔ tests. No modifica código de producción. Herramientas: Read, Grep, Glob y Bash.

Qué revisa
  • Cobertura de BR/WF/POL/SM, transacciones, contratos de datos, efectos, autoridad front/back, UNR implementados como hechos, tests y trazabilidad
Severidad
  • CRITICAL: dinero, inventario, seguridad o corrupción de datos
  • HIGH: workflow o estado incorrecto
  • MEDIUM: comportamiento secundario o test faltante
  • LOW: trazabilidad o mantenibilidad
Salidas
  • Hallazgos → regresan al orquestador (hardening)
  • SPEC GAP → regresa a la revisión humana o a clarion-expert

Reglas de frontera y estado del piloto

Reglas que no se rompen

  • El código destino se genera a partir del spec aprobado + arquitectura + skills, nunca del .txa.
  • El orquestador y el revisor no usan Clarion para reinterpretar el negocio; si falta algo, es un SPEC GAP.
  • Las anomalías del legacy se conservan, se explican y se marcan como unresolved; no se corrigen en silencio.
  • Los IDs (BR-PED-017, WF-PED-INVOICE…) no se renumeran nunca.
  • Un UNR-* implementado como hecho sin decisión humana es un hallazgo severo.
